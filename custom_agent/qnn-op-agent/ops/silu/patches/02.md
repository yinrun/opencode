# Patch 02 — Offline context-binary path + .fp16 op variant

## Date
2026-05-28

## Hypothesis history
- L1 (P01): runtime --op_packages doesn't route addNode → use offline ctx-binary
- L2 (this patch): op name needs `.fp16` suffix matching ReluFp16 canonical pattern

## Tests
1. Built x86_64-linux-clang variant of op-package using added Makefile target
2. Built x86_64 variant of model.so (linked against linux QnnModelPal.cpp)
3. Generated `silu_ctx.bin` via `qnn-context-binary-generator` (succeeded, 45KB)
4. Ran `qnn-net-run --retrieve_context silu_ctx.bin --op_packages ...`
5. Tried op name `HESiLU.fp16` with optimization rewrite `HESiLU→HESiLU.fp16`

## Result
Same broken output as runtime path:
- cosine vs ref: 0.030
- output range -512..512 (ref range -0.28..4.97)
- output unique values: structured grid `{0, ±0.0078125, ±2.0, ±0.957, 512}`

## Conclusion
**Both runtime AND offline paths produce identical broken output.** This falsifies L1's specific blame on runtime registration — the issue is upstream of execution path choice.

The output pattern (1/128 quant grid + extreme -512/+512 values) suggests:
- HTP IS executing _something_, but not our kernel
- HTP appears to apply default uint8 quantization to fp16 inputs
- Our op-package may be loaded but op symbol resolution fails silently → fallback to "Identity with quantization wrapper"

## Open questions
1. Why does context binary generate successfully if our op isn't registered?
2. Is there a missing field in QnnOpPackage_Info_t (sg_packageInfo) that lists supported op names?
3. Does sg_opNames need `"HESiLU.fp16"` listed, not just `"HESiLU"`?
