# silu/patches/04.md — fp16 PASS, root cause: qnn-net-run default I/O dtype

## Status
**COMPLETED** — fp16 cosine = 0.99999994 (≥ 0.999 acceptance), fp32 cosine = 1.0000038

## Hypothesis (this iteration)
03.md 之前判定 fp16 输出乱码是 HVX kernel dispatch 问题或需要 converter 流程。
但 fp32 路径已验证完全正确（cosine 1.0000038），说明 op-package 本身没问题。
怀疑剩余唯一变量：**fp16 数据在 host ↔ device 之间的 I/O 编码方式**。

## Action
对比 `qnn-net-run --help` 输出，发现两个被忽略的 flag：
```
--use_native_input_files   without this, files parsed in floating point (fp32)
--use_native_output_files  without this, files generated in floating point (fp32)
```

也就是说 default 行为下：
- 输入 .raw 被当 fp32 读取（4 byte/元素），不管 graph 的 native dtype 是不是 fp16
- 输出强制转 fp32 写出（`output.raw` 总是 fp32）

我们之前的 fp16 测试给的是 fp16 .raw（2 byte/元素），qnn-net-run 当 fp32 读 → 字节错位 → 输入垃圾。
读出来的 `output.raw` 是 fp32 字节，被我们当 fp16 解析 → 又错位 → 输出"垃圾但结构化"。
两次错位叠加给出稳定的 cosine ≈ 0.03 + 离散值 pattern。

## Result
重跑命令加上两个 native flags：
```bash
qnn-net-run --backend libQnnHtp.so --retrieve_context silu_ctx.bin \
  --input_list input_list.txt --output_dir output \
  --op_packages libQnnHtpSiLU.so:SiLUInterfaceProvider:CPU,htp/libQnnHtpSiLU.so:SiLUInterfaceProvider:HTP \
  --use_native_input_files --use_native_output_files
```

输出文件变成 `output/Result_0/output_native.raw`（注意名字也变了）。
对比 numpy fp16 reference：

```
SiLU fp16 [1,1,128,4864]
input  first 8: [0.30469, -1.04004, 0.75049, 0.94043, -1.95117, -1.30176, 0.12781, -0.31616]
ref    first 8: [0.17542, -0.27148, 0.50977, 0.67627, -0.24280, -0.27832, 0.06799, -0.13330]
device first 8: [0.17542, -0.27148, 0.50977, 0.67627, -0.24280, -0.27832, 0.06799, -0.13330]

cosine       = 0.99999994
max_abs_err  = 1.22e-4   (= 1 fp16 ULP)
mean_abs_err = 1.90e-8
```

逐元素**完全一致**到 fp16 表示精度。

## What I learned
1. 调试设备输出"结构化垃圾"时，**先怀疑 I/O dtype 不匹配**，不要先怀疑 kernel dispatch
2. fp32 验证是必走的一步：fp32 默认 I/O 就是 fp32，能完美隔离 dtype 问题
3. 这个错误模式（cosine 0.03 + 离散值）是 fp16/fp32 字节错位的特征指纹
4. SDK 自带的 `Relu.fp16` canonical example 表面"不通"，根本原因也是同一个 — 不是 SDK 有 bug，是我没读 `--help`
