# HEDiv iter 01 — element-wise fp16 division

## Hypothesis
Div is structurally identical to mul/sub/add: 2 input element-wise op,
output_shape == input_shape, no broadcasting needed (spec guarantees same shape).
Reuse the proven add/mul template:
- Register Tensor (quant fallback) + PlainFloatTensor + PlainFloat16Tensor variants
- DEF_TENSOR_PROPERTIES with both input placeholders ("in0", "in1")
- Naive kernel: load fp16 -> promote to fp32 -> divide -> store back as fp16

## What was built
- `src/HEDiv.cpp` — 3-variant registration + scalar 4D nested loop kernel
- `src/HEDivInterface.cpp` — standard OpPackage interface (HEDivPackageInterfaceProvider)
- `model_src/model_div.cpp` — single-node graph "Div_graph" with 2 fp16 inputs + 1 fp16 output
- `Makefile` — three targets (hexagon-v81, aarch64-android, x86_64-linux-clang)

## Build
- `make all` -> all 3 .so produced (hex 63 KB, arm 1.2 MB, x86 3.2 MB)
- `make model` -> libQnnDivModel.so 2.4 MB

## Run
Device exec via `qnn-net-run` with `--use_native_input_files --use_native_output_files`,
`--op_packages <arm>:HEDivPackageInterfaceProvider:CPU,<hex>:HEDivPackageInterfaceProvider:HTP`,
custom `htp_config.json` referencing graph_name "Div_graph".

## Result (vs numpy fp32->fp16 reference)
- cosine = 1.0000000000000002
- max_abs_err = 0.0
- relative_error = 0.0
- shape [1, 1, 128, 896], 114688 fp16 elements

**Bit-exact** match. Same outcome as add/sub: a single fp16 round on the result of
the fp32 division produces identical bytes to numpy's `np.float32(a)/np.float32(b)` cast
to `np.float16`. fp16 -> fp32 promotion is lossless, division done in fp32, then one
fp16 round closes the loop.

## Verdict
PASS (cosine >= 0.999, max_abs <= 1e-3). 1 iteration.
